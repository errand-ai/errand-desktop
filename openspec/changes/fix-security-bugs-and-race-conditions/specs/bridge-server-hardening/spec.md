## ADDED Requirements

### Requirement: BridgeServer rejects connections from non-local peers
The BridgeServer SHALL validate the remote address of every incoming TCP connection and immediately close connections that do not originate from 127.0.0.1 or the host's active vmnet gateway address.

#### Scenario: Connection from LAN device is rejected
- **WHEN** a TCP connection arrives with a remote IP that is not 127.0.0.1 and not the vmnet gateway
- **THEN** the BridgeServer closes the connection without reading any data and logs a warning

#### Scenario: Connection from loopback is accepted
- **WHEN** a TCP connection arrives from 127.0.0.1
- **THEN** the BridgeServer proceeds to read and handle the HTTP request normally

#### Scenario: Connection from vmnet gateway is accepted
- **WHEN** a TCP connection arrives from the host vmnet gateway IP
- **THEN** the BridgeServer proceeds to read and handle the HTTP request normally

---

### Requirement: /litellm-login requires one-time token
The BridgeServer SHALL NOT serve the LiteLLM login page without a valid one-time token. The token SHALL be generated by an authenticated `GET /litellm-login-url` endpoint and be valid for 60 seconds, single use only.

#### Scenario: /litellm-login with valid OTP succeeds
- **WHEN** a request arrives at `GET /litellm-login?token=<valid-otp>`
- **THEN** the BridgeServer serves the LiteLLM auto-login HTML and invalidates the token

#### Scenario: /litellm-login with missing or expired token is rejected
- **WHEN** a request arrives at `GET /litellm-login` with no token, an invalid token, or a token older than 60 seconds
- **THEN** the BridgeServer returns HTTP 401 Unauthorized

#### Scenario: /litellm-login-url requires bearer token
- **WHEN** a request arrives at `GET /litellm-login-url` without a valid Authorization bearer token
- **THEN** the BridgeServer returns HTTP 401 Unauthorized

#### Scenario: /litellm-login-url returns a URL with a fresh OTP
- **WHEN** an authenticated request arrives at `GET /litellm-login-url`
- **THEN** the BridgeServer returns a JSON body `{"url": "http://localhost:9876/litellm-login?token=<otp>"}` where the OTP is a cryptographically random string of at least 32 characters

### Requirement: Bridge routes validate container ID format
The BridgeServer SHALL reject any request where the container ID extracted from the URL path does not match the pattern `^[a-zA-Z0-9_-]{1,128}$`.

#### Scenario: Request with valid container ID is processed
- **WHEN** a request arrives at `/containers/<id>/status` and `<id>` matches `^[a-zA-Z0-9_-]{1,128}$`
- **THEN** the BridgeServer routes the request to the appropriate handler

#### Scenario: Request with path-traversal characters is rejected
- **WHEN** a request arrives at `/containers/../etc/passwd` or any path whose parsed ID contains `/`, `.`, or other non-allowed characters
- **THEN** the BridgeServer returns HTTP 400 Bad Request

---

### Requirement: HTTP request body size is limited
The HTTP parser SHALL reject any request with a Content-Length header value exceeding 10 MB.

#### Scenario: Request with body exceeding 10 MB is rejected
- **WHEN** an HTTP request is received with `Content-Length` greater than 10,485,760 bytes
- **THEN** the parser returns a parse failure and the BridgeServer returns HTTP 413 Request Entity Too Large

#### Scenario: Request with body within limit is parsed normally
- **WHEN** an HTTP request is received with `Content-Length` ≤ 10,485,760 bytes
- **THEN** the parser reads the body and returns a valid HTTPRequest

---

### Requirement: Race condition in connection handlers is eliminated
Connection state handlers in `DockerHTTPClient` and `HealthChecker` SHALL use a `Mutex`-protected flag to ensure the underlying continuation is resumed at most once.

#### Scenario: Concurrent state callbacks do not double-resume
- **WHEN** `NWConnection.stateUpdateHandler` is invoked concurrently from multiple threads with both `.ready` and `.failed` states
- **THEN** the continuation is resumed exactly once and no crash occurs

---

### Requirement: Secrets directory has restrictive permissions
The secrets directory (`~/Library/Application Support/ErrandDesktop/secrets/`) SHALL be created with POSIX permissions `0o700` so only the owning user can read it.

#### Scenario: Directory is created with 0o700
- **WHEN** the secrets directory does not exist and KeychainManager creates it
- **THEN** the directory is created with POSIX permissions `0o700`

---

### Requirement: Log buffer is bounded
The in-memory log buffer in `AppState` SHALL never exceed 10,000 entries. When the limit is reached, the oldest entries SHALL be discarded.

#### Scenario: Log buffer is capped after 10,000 entries
- **WHEN** `appendLog` is called and the log buffer already contains 10,000 entries
- **THEN** the oldest entry is removed before the new entry is appended, keeping the count at 10,000

---

### Requirement: PortForwarder is actor-isolated
`PortForwarder` SHALL be declared as a Swift `actor` so all access to its mutable state is serialized by the actor executor.

#### Scenario: Concurrent forward calls do not corrupt state
- **WHEN** `forward(localPort:to:remotePort:)` is called concurrently from multiple tasks
- **THEN** the `rules` array is modified without data races and each rule is independently registered
